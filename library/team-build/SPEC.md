# team-build

Once, at project creation, read the project brief, decompose it into the
capabilities the work will need, pick the best library skill for each need,
and write the project's `skills-manifest.yaml` with a record of why each
pick won over its nearest neighbour.

Status: spec approved for build, 2026-10-03. Built 2026-10-03; first eval run 2026-10-03 fixed needs (cite brief phrase), precision (read in full), set-cover (covered_by concession, not not_for or also_covers) and low-confidence handling. Run 3 added a second opinion in precision for noisy replies (low, or self-contradicting pick or covered_by). Canonical library stays as is;
this is a new library skill plus one generated index file.

## Why this exists

`select.md` already writes a manifest, but it picks from one-line catalog
descriptions after one question to the user. That is fine for an obvious
project and fails exactly where the library is dense: writer vs editor vs
writing-team vs aimm-writing-team, checkpoint vs session vs context-mgr,
audit-fix vs gauntlet vs skill-auditor. The failures are precision failures
between near neighbours, not recall failures. team-build spends tokens where
select does not: a dense index per skill, a need-by-need pick with the
runner-up named, and a reason the user can audit later.

Runs once per project, so cost and latency are secondary to precision,
recall, and the value of the resulting team.

## Inputs

- The project brief: whatever the user supplies (a paragraph, a README, a
  folder to `ls`). If it is thin (no stated purpose, or under about 50
  words), ask three fixed questions inline before stage 1: what the project
  produces, who it is for, and what kinds of tasks the user will ask for
  most. The answers are appended to the brief. No handoff to the
  ambient-folder interview.
- `library/catalog.yaml`: the authoritative list of skills (68 today).
- `library/team-index.yaml`: the dense index, generated (see below).
- `~/.aai/skills-manifest.yaml`: user-scope picks already in force; never
  re-propose those. team-build writes project scope only and never edits
  the user manifest.

## The index (`library/team-index.yaml`)

One entry per catalog skill, generated by a build script from the skill's
`instructions.md` and its catalog line. Fields:

```yaml
writer:
  description: <catalog line, verbatim>
  summary: |        # Chain-of-Density summary, 150 to 250 words, written for
    ...             # matching: names the inputs it needs, the artifact it
                    # produces, what it refuses to do, and its stage in any
                    # pipeline it belongs to
  requests:         # 5 to 8 synthetic user requests it should win
    - "turn these notes into a first draft of the LinkedIn post"
    - ...
  not_for:          # near-neighbour contrasts, generated against the catalog
    - editor: "the draft already exists and needs tightening"
    - writing-team: "the user wants research and editing done too"
  stage: draft      # free text, used by set-cover (research, draft, edit, publish, audit, ...)
  source_hash: <sha1 of instructions.md + catalog line>
```

Build: `scripts/build-team-index.py [--check]`. For each skill whose
`source_hash` changed, one inference call writes `summary`, `requests`,
`not_for`, `stage` from the skill body plus the full catalog (so contrasts
name real neighbours). Unchanged entries are kept verbatim; the index is
committed. `--check` fails on any stale hash, and `audit-distribution.py`
runs it. Nothing reads skill bodies at team-build time except the precision
step below.

Size budget: 68 entries at roughly 600 tokens each is about 40K tokens. That
fits one context comfortably, which is the whole reason this design needs
no embeddings and no external scorer today. Ceiling: around 300 entries the
index stops fitting one pass; see "Jev" below for what changes then.

## Pipeline

All stages run inside one skill invocation. Stages 2 and 3 are inference;
the rest is code or plain file I/O.

1. **Brief in, needs out.** One inference pass over the brief produces a
   list of needs, up to 10, each quoting the brief phrase it came from, each one sentence in the shape of a request the
   user will actually make ("draft articles from research notes", "publish
   finished pieces to the hub", "keep context across sessions"). Needs are
   the unit everything downstream works on. Rewrite the brief here, not
   later: each need is already the rewritten query.

2. **Recall: shortlist per need.** One pass with the whole index and all
   needs in context. For each need, return up to 5 candidates ranked, each
   with the one line from the index that earned it a place. Output is
   structured (YAML), validated by code: every candidate must be a catalog
   name, else the pass is rerun once with the error quoted.

3. **Precision: pick per need.** For each need, a fresh-context subagent
   gets the need, the brief, and the full `instructions.md` of the top 3
   candidates (not the index). It returns:

   ```yaml
   need: draft articles from research notes
   pick: writer
   runner_up: writing-team
   reason: brief says research is done by a human; writing-team would redo it
   confidence: high | medium | low
   ```

   Fresh context per need keeps one pick from biasing the next and keeps
   the main thread small. `confidence: low` or a reason that says the
   candidates are interchangeable is surfaced to the user as a question,
   not resolved silently.

4. **Set-cover.** Code. Each stage 3 reply carries `covered_by`: a
   shortlist skill, picked for another need, that the reader concedes
   handles this need too. If need n says `covered_by: A` and A is a pick
   elsewhere, drop need n's pick B and record the subsumption. The
   direction matters: the second eval run let picks claim other needs
   (`also_covers`) and that dropped writer, init-dev-project, gmail-triage
   and aimm-newsletter, each rejected by the reader of the need it was
   claimed for. The index's `not_for` is not used here: sibling skills name
   each other in both directions, so it cannot rank them (the first eval
   run dropped gmail-manager, vibe, meeting-nuggets and
   teaching-block-synthesized that way). If two needs picked the same
   skill, merge. Picks already in the user-scope manifest are dropped from
   the project manifest and noted. A `low` confidence pick never enters the
   manifest; it is shown as a gap question.

5. **Confirm and write.** Show the table (need, pick, runner-up, reason)
   plus any open questions. On yes, write:

   - `<project>/skills-manifest.yaml`, the usual `domain_skills:` list with
     a `# need: ...` comment per entry so the file reads on its own.
   - `<project>/.aai/memory/team-build-<date>.md`: brief as received, the
     needs, the shortlists, every pick with runner-up and reason, dropped
     picks and why, questions asked and answers. This is the audit trail
     and the eval corpus seed.

## Outputs

- `skills-manifest.yaml` (project scope).
- `.aai/memory/team-build-<date>.md` rationale record.
- Nothing is vendored into `.ailib/`; that remains lifecycle's job, and
  team-build can hand the manifest to it when the user asks.

## Jev: checked, not used

Contract as of 2026-10-03 (docs.typesafe.ai): `POST /v1/systemone` with a
`state` object and typed `questions`; a Noul returns a probability 0 to 1
per question; one call per (need, candidate) pair; calls are independent
and parallel; jev-1.12 lists $0.042 per 1M input tokens, output free; 429
on rate limit with no published quota; no latency figures; no calibration
claim for any domain, and the docs say thresholds must be validated on
your own data.

What it would do here: a grid of needs by candidates with a number in each
cell. At 8 needs by 68 skills by about 1.5K tokens that is under $0.05 and
would run in seconds. Cheap is not the question. The question is what the
number replaces, and the answer today is nothing:

- Recall over 68 entries is one long-context pass that already returns a
  ranked shortlist with a quoted reason. A Noul gives a number without the
  reason, and the reason is the deliverable.
- The precision pick needs the skill bodies and a written contrast. Jev
  does not produce prose.
- There is no labeled corpus yet, so a Jev score could not be checked. A
  calibrated-looking number nobody has validated is worse than a ranked
  list with visible reasons.

Jev earns a place when either condition holds, and the spec should be
reopened then, not before:

1. The catalog outgrows one context pass (about 300 entries). Jev becomes
   the fast-search stage: Noul "could this skill do this need" per pair,
   top 5 per need into the precision step. It beats embeddings there because
   the question carries the criteria and the output is a probability, not a
   cosine.
2. The eval set below shows recall misses at stage 2 that a per-pair
   scorer fixes. Measure first.

## Evals

Write these before the skill body, per the skill-authoring rules.

- **Corpus:** 20 project briefs, labeled with the expected manifest and the
  runner-up per need. Source them from real folders already stamped
  (aimm-kb-agent, the projects in `in-progress/`, Lou's client folders) and
  from the rationale records this skill writes once it runs.
- **Near-miss cases:** at least 6 briefs built to split neighbours: draft
  only vs full pipeline; checkpoint vs session vs context-mgr; audit-fix vs
  gauntlet; publish-article vs aimm-newsletter.
- **Metrics:** recall at 5 on stage 2 (expected pick in the shortlist),
  precision at 1 on stage 3, and reason quality judged pass/fail by a
  second agent against the labeled runner-up ("does the reason name the
  real difference").
- **Baseline:** run `select.md` on the same corpus. team-build must beat it
  on precision at 1 or it is not worth its tokens.
- **Triggering:** should fire on "build the team for this project", "which
  skills should this project use", "set up capabilities for X", a fresh
  ambient-folder stamp with a brief; should not fire on "use the writer
  skill", "add editor to this project" (that is manage), or any single
  task request.

## Sharing the index

The per-request router reads only `catalog.yaml` and must keep doing so;
its budget is one description line per skill. `team-index.yaml` is for
team-build only. If the router later needs the `not_for` contrasts for
its own tie-breaks, it reads that one field for the two tied skills, never
the whole index.
